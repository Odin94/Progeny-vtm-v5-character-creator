Static architecture assessment · 3 September 2026

Progeny architecture improvements

A codebase-design assessment focused on deep modules: small interfaces that hide meaningful behavior, improve locality, and provide a stable test surface.

Recommendation: strengthen shared contracts first. The largest risk is not file length; it is one character or realtime change needing coordinated edits across several independently maintained interfaces.

1. Character contract P0

The persisted character interface is duplicated in the frontend model and backend schema. The backend deliberately makes its version partial, while the frontend performs compatibility patches and strict parsing in characterData.ts.

This makes the storage seam shallow: callers need to know which side validates, which side repairs old data, and which code parses JSON. A concrete divergence already exists: the frontend includes characterVersion, while the backend schema does not. A partial top-level schema also accepts an empty character payload that the frontend cannot render as a valid character.

decodePersistedCharacter(raw): Result<Character, ContractError> encodeCharacter(character): PersistedCharacter migrateCharacter(raw): PersistedCharacter

Create a side-effect-free character-contract module containing the canonical Zod schemas, version metadata, and decode/encode behavior. Make the backend persist only current-format data. Test the interface end-to-end: a value written through the backend must decode through the frontend without repair.

2. Realtime protocol P1

The client chat store and server protocol module separately maintain the same message family. The server uses runtime Zod validation, but the client casts parsed messages directly to a TypeScript union.

Extract a realtime-contract module that exports client-to-server and server-to-client Zod schemas plus inferred types. The client should parse received messages at that interface. This is an in-process dependency, so it does not need an adapter. The existing fake WebSocket remains an appropriate transport adapter for store tests.

3. Versioned private notes P1

Character notes and coterie notes independently perform version queries, writes, duplicate cleanup, pruning, and restoration. privateNotes.ts shares only the policy calculations.

load(scope, userId): NoteHistory save(scope, userId, content): SaveResult restore(scope, userId, versionId): SaveResult

Deepen this into a VersionedPrivateNotes module. Use character-note and coterie-note table adapters to satisfy one narrow note-store interface. Keep authorization, route parsing, and tracking at the route seam. Replace duplicated route-level behavior tests with tests at this module’s interface.

4. Coterie and Homebrew behavior P2

coteries.ts mixes membership, invitations, notes, live vitals, identity visibility, and chat lifecycle. homebrew.ts mixes authoring, coterie attachment, library reads, publication, moderation, ratings, and comments.

Do not replace either with a single wide facade. Extract behavior-focused modules with small interfaces: CoterieReadModel, CoterieMembership, CoterieInvites, HomebrewCollections, HomebrewLibrary, and HomebrewModeration. Each should own its authorization, persistence, and response shaping; route registration becomes transport-only.

5. Frontend HTTP transport P2

api.ts usefully centralizes cookie credentials, CSRF, uploads, and error behavior. Its exported object, however, contains approximately 55 unrelated operations and response types.

Preserve the deep core transport—request, requestBlob, and upload—then expose feature modules for auth, characters, coteries, Homebrew, administration, and recent changes. This reduces the interface a caller must understand without duplicating security behavior.

6. Generator seam and documentation P3

The current generator step module is already a strong deep module: it owns step visibility, normalization, ordering, and progression. The architecture documents still describe the retired numeric step-offset mechanism.

Update frontend architecture documentation and frontend guidance to name steps.ts as the navigation seam. This is a low-cost change that preserves an important improvement already present in the implementation.

Suggested sequence

  1. Introduce the character-contract module with cross-application round-trip tests.
  2. Introduce the realtime-contract module and validate client-side inbound messages.
  3. Extract VersionedPrivateNotes, moving existing behavior tests to its interface.
  4. Slice coterie and Homebrew behavior incrementally, one cohesive module at a time.
  5. Split the frontend HTTP façade after its feature contracts are stable.

Assessment method: static review of the frontend and backend source, architecture guides, and existing tests. No production behavior was changed by this report.
