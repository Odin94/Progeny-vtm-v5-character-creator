# Performance investigation, 3 October 2026

Baseline: `4a93b197f410868ea2193b055742279a3f0c1492` (main at the start of this investigation).
After for the numerical samples: `2e3694df3c96d2db92ab65d9429017873a827187`.
The following correctness fix merges same-batch updates from separate consumers; rerunning
the benchmark preserves zero redundant schema parses, zero chat-control commits and zero
Free-mode XP stat-row renders. Both measured revisions use identical lockfiles,
Node 24.15.0 and pnpm 10.33.0 on an Apple M5. Raw samples are in
[`2026-10-03-results.json`](./2026-10-03-results.json).

The investigation follows [Vercel React Best Practices](https://github.com/vercel-labs/agent-skills/blob/main/skills/react-best-practices/SKILL.md),
with rendering and rerendering treated as critical. The application already lazy loads its
routes and generator PDF export, uses Zustand selectors, and memoizes sheet sections and
rows. The remaining measured problems were a heavy static export import, broad chat
subscriptions, eager character validation during renders, and unnecessarily broad XP
dependencies in stat rows.

## Production loading

| Measurement | Before | After | Change |
| --- | ---: | ---: | ---: |
| Sheet JavaScript, static dependency closure | 3,358,104 B | 2,217,481 B | −34.0% |
| Sheet JavaScript, sum of per-chunk gzip sizes | 1,235,288 B | 728,963 B | −41.0% |
| Initial entry JavaScript | 1,968,114 B | 1,968,240 B | +126 B |

`CharacterSheetMenu` loaded the PDF exporter, PDF library and embedded font support on every
sheet visit. The export action now imports that code when clicked, matching the generator.
The menu closes immediately, and import/export failures still open its existing error dialog.
The exporter and its assets are still available when requested.

These are production Vite manifest measurements, recursively counting static `imports`
once per entry and excluding dynamic imports, CSS, images and source maps. Gzip sizes are
local compression estimates, not a statement about server compression configuration.
The initial-entry number and sheet number overlap; they must not be added together.
The browser check independently observed exactly the same sheet JavaScript totals before
and after. This is a loading-work reduction, not a measured 34% improvement in LCP or INP.

## React interaction work

The benchmark mounts real Mantine sheet components in React/jsdom, uses real Zustand
stores and the real local-storage character hook, and measures React Profiler work. A thin
wrapper counts actual attribute/skill pip renders without replacing their implementations.
Each update is committed separately with `act`, so React batching cannot hide repeated work.
Baseline and after runs are interleaved seven times; the table contains medians of each
complete interaction sequence. These are development-renderer microbenchmarks, not browser
interaction latency measurements.

| Sequence | Before | After |
| --- | ---: | ---: |
| 100 unrelated chat/participant updates: dice-control commits | 100 | 0 |
| Same sequence: React render work | 41.91 ms | 0 ms |
| 30 name edits: character schema parses | 30 | 0 |
| Same sequence: React render work | 2.95 ms | 1.01 ms |
| 30 hunger edits: character schema parses | 30 | 0 |
| Same sequence: React render work | 43.70 ms | 40.35 ms |
| 30 XP edits in Free mode: stat-row renders | 1,044 | 0 |
| Same sequence: React render work | 234.57 ms | 0.81 ms |
| 30 XP edits in XP mode: stat-row renders | 1,080 | 1,080 |
| Same sequence: React render work | 493.91 ms | 452.71 ms |

The large reductions have deterministic work-count evidence. The smaller hunger/XP-mode
timing differences are noisy and should not be interpreted as guaranteed latency gains.
The mounted parent still commits each persisted edit; necessary view changes remain synchronous.

Changes:

- `useSessionChat` accepts shallow selectors. Dice controls subscribe only to connection,
  session ID and their send action; account/coterie pages also select only what they use.
  The chat window keeps its full subscription. Connection changes still refresh controls.
- Mantine evaluates its storage reader as a `useState` argument on every hook render.
  The character hook now lazily creates its default and keeps one latest validated serialized
  snapshot shared by subscribers. Its serialization path refreshes the snapshot on local
  edits. A different external storage value still runs compatibility migration and Zod
  validation. Storage writes stay immediate and the existing recovery path is preserved.
  Functional setters read that shared snapshot, so two mounted consumers updating in one
  React batch merge correctly. External storage changes, deletion and invalid-data recovery
  also refresh/reset the snapshot before a local updater can run in the same batch.
- Attribute/skill memo comparators use available XP only in XP mode. Free/Play mode stat
  controls do not depend on XP. Skill notes compare the specialty-note slice. The comparators
  also refresh ownership/edit-disable changes and replacement setters, preserving correctness.

The edit harness mounts Attributes, Skills and BottomData rather than the entire application
shell. Name typing is already debounced in the real sheet; these sequences measure persisted
character updates after that debounce, not every raw keyboard event.
The production browser smoke test confirmed edited names survive reload after the existing
debounce settles and PDF export loads its separate chunk and generates the download without
console errors. A 13-keystroke name check showed no browser typing speedup (median 2.2 ms
before versus 2.4 ms after, with the same mutation count); the improvements above concern
removed dependency/render work and do not justify claiming faster raw name typing.

## Backend authorization lookup

`getCharacterAccess` is used by character reads and private-note access. It rebuilt Drizzle
SQL and prepared SQLite statements on each call, then loaded an entire share row for a boolean
existence check. It now lazily prepares parameterized character/share queries once and selects
only the share ID. The owner path still skips the share query. This caches statements, never
authorization results or character data; revocation, deletion and updated character versions
are read immediately.

| Helper call | Before median | After median | Reduction |
| --- | ---: | ---: | ---: |
| Owner | 0.04185 ms | 0.00521 ms | 87.6% |
| Shared reader | 0.07686 ms | 0.00739 ms | 90.4% |
| Unauthorized user | 0.07545 ms | 0.00707 ms | 90.6% |
| Missing character | 0.03907 ms | 0.00299 ms | 92.4% |

The script forces a disposable in-memory SQLite database before dynamically importing the
database module. It seeds one character with 10 KB of data, one share and the character-share
index used by these lookups. Each scenario has 100 warmups and seven samples of 2,000 calls,
checking the access result on every call. The benchmark measures actual application helper
code, but excludes HTTP, WorkOS authentication, telemetry and disk/network contention. These
percentages therefore apply to this helper, not complete API requests or production throughput.

## Reproducing

From the repository root, with dependencies installed:

```sh
pnpm --dir frontend exec vite build --manifest
pnpm --dir frontend exec node scripts/benchmarkBundle.mjs build
pnpm --dir frontend exec vitest run benchmarks/rendering.test.tsx --maxWorkers=1
pnpm --dir backend exec tsx scripts/benchmarkCharacterAccess.ts
```

For a baseline comparison, create a detached worktree at the baseline hash, install the same
locked dependencies, and copy only the three benchmark scripts into that worktree. Run the
same commands there. To match the recorded interaction results, alternate baseline and after
for seven samples and compare medians, avoiding unrelated heavy local processes.

Validation includes frontend/backend formatting and lint, frontend `tsc --noEmit`, backend
TypeScript build, frontend production build, full unit suites, real permission/XP-affordability
regressions, cross-tab validation and sequential local-store updates, and fresh backend data/
revocation/deletion behavior. Production UI checks cover the sheet, persisted edits and menu
navigation; the PDF export keeps its existing regression suite.

## Remaining opportunities

The initial app dependency closure is still about 1.97 MB of JavaScript; reference data and
the analytics SDK warrant separate user-journey chunk analysis. XP-mode affordability changes
legitimately affect all stat rows and still cost meaningful render work; coarse memoization must
not hide changed rules. Skills currently uses per-row resize observers and window listeners;
CSS container queries could remove that layout work after careful responsive-layout verification.
Long sessions and large homebrew libraries deserve browser traces with realistic datasets.
This investigation makes no claims about authenticated production API or device-specific INP
without that separate evidence.
